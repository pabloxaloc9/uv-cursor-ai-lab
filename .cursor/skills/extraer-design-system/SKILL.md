# Extraer un design system

1. Leer producto, stack y sección 3 de entregables/EQUIPO.md. Pedir dos capturas con empresa, URL y qué interesa de cada una si no están disponibles. No navegar o afirmar que se han visto imágenes que no se han recibido. Si solo hay descripciones, declarar esa limitación.
2. Preguntar qué tres cualidades quiere transmitir la marca y quién usará la interfaz. Esperar respuesta; como subagente, enviar las preguntas al principal.
3. Devolver una tabla por referencia con evidencia: jerarquía, densidad/espacio, color, tipografía aparente, componentes y navegación. Marcar «observado», «estimado» o «no determinable». Una captura no identifica con certeza el nombre de una fuente ni todos los estados.
4. Proponer un sistema propio con justificación y trazabilidad: qué se toma de cada referencia y qué se adapta al producto. No copiar logos, marca, textos o activos. Usar fuentes de sistema por defecto si evitan una dependencia; si se propone otra fuente, justificar origen y licencia antes de descargar.
5. Concretar los tokens semánticos mínimos: fondo, superficie, texto, texto secundario, primario, texto sobre primario, borde, error, éxito y foco. Elegir valores de color para la propuesta y una escala de espacio consistente, radios y jerarquía tipográfica. Identificar colores estimados de la captura frente a valores nuevos elegidos para la marca.
6. Describir botones, campos, tarjetas, navegación y listado/agenda o balance. Incluir estados normal, foco, deshabilitado cuando proceda, vacío, error y éxito; acompañar color con texto o icono etiquetado. Exigir etiquetas y foco visible. El contraste se mide con una herramienta cuando esté disponible; no afirmar una ratio por intuición ni certificar accesibilidad completa.
7. Presentar como máximo dos direcciones compactas. Esperar elección y ajustes del equipo. Guardar solo la decisión final en la sección 3 del cuaderno, con referencias y cualquier comprobación pendiente. Los valores se traducen al código tras aceptar arquitectura; no crear archivos de un framework antes.
8. En una revisión posterior, comparar el prototipo visible con los tokens y componentes acordados. Informar desviaciones concretas; no sustituir el sistema por una propuesta nueva sin decisión del equipo.

Resultado: sistema pequeño aplicable al flujo obligatorio, con observaciones separadas de propuestas. No producir un manual extenso, una copia de una web o una dependencia de un servicio de pago.
